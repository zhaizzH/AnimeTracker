# AnimeTracker 前端重建设计

## 1. 背景与目标

AnimeTracker 后端业务、Agent 与数据导入能力已经完成。现有 `frontend/client` 和 `frontend/admin` 不作为新前端的架构或视觉基线；新前端从空工程重新设计和实现，但继续使用现有后端接口与业务规则。

重建目标如下：

- 以 Client 为第一优先级，完整交付发现、追番管理与 AI 交互体验。
- 第二阶段完整覆盖 Admin 已有后端能力。
- Client 直接使用 SSR，使公开页面可被搜索引擎收录并支持分享预览。
- Client 与 Admin 作为两个独立站点部署，同时在一个前端 monorepo 中共享稳定的工程边界。
- 桌面端与移动端同等重视，使用完整响应式布局。
- 首版只提供简体中文，但从架构上支持以后增加日文和英文。

产品边界明确排除在线播放、评论、动态、关注、私信等社区能力。产品专注于番剧发现与资料浏览、个人收藏与观看进度、放送时间表，以及 AI 搜索、推荐和收藏操作。

## 2. 已确认的产品原则

### 2.1 Client 定位

Client 同时突出追番管理与 AI 助手：传统页面负责确定、可浏览的资料与管理任务，AI 负责自然语言搜索、发现、推荐和受控业务操作。

AI 不占用主导航位置。它默认以首页及其他主页面右下角的常驻入口出现：桌面端展开为悬浮聊天窗，移动端展开为底部面板并可上拉进入全屏。

### 2.2 首页状态

首页根据登录状态自适应：

- 未登录：首页突出本季新番、热门作品、今日放送和搜索入口。
- 已登录：首页突出继续观看、今日更新、收藏概览和个性化发现。

首页不堆叠所有功能。未登录状态承担发现，登录状态承担“今天该看什么、接着看什么”。

### 2.3 功能范围

Client 首版完整覆盖：

- 注册、登录、邮箱验证、忘记密码和重置密码。
- 首页、搜索与筛选、番剧详情、放送时间表。
- 收藏状态、评分、自定义标签和观看进度。
- 个人资料、邮箱、密码、主题和语言偏好。
- AI 流式对话、会话历史、工具状态和写操作确认。

Admin 第二阶段完整覆盖：

- 运营仪表盘。
- 番剧资料与剧集管理。
- 用户与角色管理。
- Bangumi 数据导入任务。
- 操作日志与审计。
- Agent 模型与提示词配置。
- 管理员 Agent 对话。

管理员 Agent 对话和细粒度权限在 Admin 基础后台之后交付，不阻塞基础管理能力。

## 3. 技术方案

采用按场景分工的 pnpm monorepo：

```text
frontend/
├── apps/
│   ├── client/                 # Next.js App Router，SSR + BFF
│   └── admin/                  # Vite React SPA
├── packages/
│   ├── api-contract/           # OpenAPI 生成类型与底层请求定义
│   ├── design-tokens/          # 色彩、字体、间距和断点
│   ├── eslint-config/
│   └── typescript-config/
├── package.json
└── pnpm-workspace.yaml
```

### 3.1 Client

- Next.js App Router 提供 SSR、Server Components、元数据和 BFF Route Handlers。
- 公开首页、搜索结果、番剧详情和时间表优先由 Server Components 获取并渲染数据。
- 筛选、收藏、进度、主题和 AI 等交互使用尽可能靠近叶子节点的 Client Components。
- Route Handlers 负责 Cookie 鉴权、Token 刷新、请求追踪、错误透传和 SSE 转发。
- 优先使用 Next.js 的服务端数据获取能力；TanStack Query 只用于频繁变化、需要客户端缓存、乐观更新或查询失效的数据。
- Client 使用轻量、低样式的可访问组件原语与 CSS Modules，实现定制的“编辑部手账”视觉。

### 3.2 Admin

- Admin 使用 Vite、React、TypeScript、TanStack Query 和 Ant Design。
- Admin 不承担 SEO 和 SSR 复杂度。
- 表格、筛选、表单、抽屉、批量操作与反馈优先使用 Ant Design 能力，再通过 token 与局部样式形成 AnimeTracker 品牌感。

### 3.3 共享边界

- OpenAPI 是接口类型的唯一来源，不手写两套重复 DTO。
- 两端只共享 API 契约、设计 token 和工程配置。
- 不建立庞大的共享 UI 组件库，也不跨端共享业务组件。
- Zustand 不作为默认依赖。只有无法由 URL、Cookie、服务端数据或局部状态表达的跨页面客户端状态才引入 store。
- Client 与 Admin 独立构建、镜像化、发布和回滚。

## 4. 信息架构与路由

### 4.1 Client 导航

桌面顶部结构：

```text
番组手账｜首页｜放送时间表｜        长条搜索栏        ｜用户菜单
```

- 顶部主导航只保留首页和放送时间表。
- 长条搜索栏常驻顶部，提交后进入 `/discover?q=...`。
- “我的追番”放入用户菜单。
- 登录首页提供“继续观看”和“查看全部追番”的直接入口。
- 未登录用户菜单显示登录与注册。
- 登录后用户菜单显示我的追番、个人资料、主题、语言和退出登录。

移动端顶部保留品牌、搜索入口和用户菜单，底部导航只保留首页和放送时间表。AI 入口避让底部导航与设备安全区域。

### 4.2 Client 路由

- `/`：按登录状态自适应的首页。
- `/discover`：关键词、季度、标签、类型、状态、排序与分页。
- `/subjects/[id]`：番剧资料、简介、标签、剧集、关联作品和收藏操作。
- `/schedule`：当前季度按星期展示，并可切换年份和季度。
- `/collections`：想看、在看、看过、搁置、抛弃，以及评分、标签和进度。
- `/profile`：个人资料、邮箱、密码、安全设置、主题和语言偏好。
- `/auth/*`：登录、注册、邮箱验证、忘记密码和重置密码。

### 4.3 Admin 导航

```text
仪表盘
内容管理
  └── 番剧与剧集
用户管理
数据导入
Agent
  ├── 运行配置
  ├── 提示词
  └── 管理员对话
审计日志
```

Admin 仪表盘只展示能引导行动的信息，例如失败导入、异常趋势和待处理数据，避免堆砌无决策价值的统计卡片。

## 5. 视觉系统

Client 使用“编辑部手账”设计语言：

- 浅色主题采用暖骨白画布、白色内容面、炭黑文字和低对比暖灰边框。
- 深色主题采用暖黑灰画布、略亮内容面和米白文字，不使用纯黑或霓虹色。
- 色彩主要来自番剧封面；界面强调色只服务于主要操作、收藏状态和反馈。
- 使用留白、排版和细边框建立层级，不使用渐变、玻璃拟态、重阴影、大面积高饱和色或过度圆角。
- 展示标题使用中文衬线字体栈，正文与操作使用清晰的中文无衬线字体栈，日期与集数使用等宽数字特征。
- 首版不依赖必须联网加载的字体，后续可以自托管品牌字体。
- 动效只使用短距离位移和透明度变化，并遵守系统的减少动态效果设置。

Client 核心组件包括：

- `SubjectCard`：封面、名称、年份或季度、评分及收藏状态。
- `SearchBar`：常驻长条搜索、建议词、历史记录和键盘选择。
- `CollectionEditor`：状态、评分、自定义标签和观看进度。
- `EpisodeProgress`：单集更新和连续进度操作。
- `ScheduleColumn`：桌面按星期组织，移动端切换为单日视图。
- `EmptyState`、`ErrorState`、`Skeleton`：完整的数据状态反馈。
- `AiLauncher`、`AiPanel`：展示容器与会话逻辑分离。

Admin 与 Client 共享品牌语义而不照搬组件。Admin 支持浅色、深色和跟随系统主题，以操作效率和信息清晰度为先。危险操作必须二次确认并明确说明影响对象。

## 6. 数据流与鉴权

### 6.1 请求路径

```text
公开读取
Browser → Next Server Component → Spring Boot

登录后读取或写入
Browser → Next Route Handler → Spring Boot

AI 流式对话
Browser → Next SSE Proxy → Spring Boot → Agent
```

### 6.2 Client 鉴权

- 登录与刷新 Token 只经过 BFF。
- Access Token 与 Refresh Token 使用 `Secure`、`HttpOnly` 和合适的 `SameSite` Cookie。
- 浏览器 JavaScript 不读取 Token。
- SSR 请求直接识别用户并渲染个性化首页。
- Access Token 失效后，BFF 只尝试一次刷新和原请求重放；失败时清理 Cookie 并返回统一未登录状态。
- 修改邮箱和密码等敏感操作要求重新验证身份。

### 6.3 Admin 鉴权

- Admin Access Token 只保存在运行时内存。
- 刷新页面、关闭标签页或内存状态丢失后必须重新登录。
- 不使用 localStorage、sessionStorage 或 IndexedDB 保存管理员 Token。
- 路由守卫除检查 Token 外，还向后端确认角色为 `ADMIN`。
- 401 或 403 会清空内存会话并进入登录页。

### 6.4 数据策略

- 搜索词、季度、标签、排序和分页保存在 URL 中，使结果可分享、可返回并可由 SSR 处理。
- 公开页面使用 Next.js 服务端数据获取和明确的缓存失效策略。
- 用户收藏、进度与 Admin CRUD 使用 TanStack Query。
- 进度等低风险操作允许乐观更新；删除、角色修改和批量变更等待服务端确认。
- 不把整份响应放入全局状态，组件只订阅需要的数据。
- 番剧详情、标签和季度数据允许短时缓存。
- 用户收藏、权限、导入状态和 Agent 配置不跨用户共享缓存。
- 登录态页面禁止进入公共 CDN 缓存。
- 数据修改只失效相关查询，不执行全站刷新。

## 7. AI 助手

### 7.1 容器与状态

- AI 入口常驻 Client 主页面右下角。
- 未登录用户可以打开并查看能力说明，发送消息时引导登录。
- 桌面端展开为悬浮聊天窗，可最小化、调整为宽版或进入专注模式。
- 移动端展开为底部面板，可上拉进入全屏并下滑收起。
- 页面切换、窗口形态变化和暂时收起不会中断 SSE 请求。
- AI 模块延迟加载，不阻塞公开页面首屏。

### 7.2 消息展示

消息按以下结构组织：

```text
用户消息
  → 可理解的处理状态
  → 工具调用状态
  → 文字回答
  → 番剧结果卡、操作预览或错误恢复
```

- 不展示模型内部推理原文，只显示“正在检索本季奇幻作品”等可理解状态。
- 推荐结果使用结构化紧凑卡片，不把长结果列表塞入 Markdown。
- 工具调用显示进行中、成功和失败，不暴露内部参数、密钥或调试信息。
- AI 回复中的番剧链接使用站内详情路由。
- 会话历史按账号保存，支持新建、切换、重命名和删除。
- 默认恢复最近一次会话，但不会自动发送消息。

### 7.3 写操作闭环

```text
用户意图
→ Agent 生成操作预览
→ 前端展示具体变更
→ 用户确认或取消
→ 后端执行
→ 前端刷新相关收藏或进度
```

操作预览必须展示受影响作品或剧集、当前值、目标值、跳过项及原因、预览有效期，以及明确的确认和取消按钮。

- 待确认操作过期后不得沿用旧按钮。
- 执行型确认提交后立即锁定，防止重复执行。
- SSE 中断后保留已接收内容并提供重新连接或重新发送。
- 关闭面板时只收起界面，不默认取消仍在生成的任务；用户可以显式停止。
- Agent 不可用时，普通搜索、收藏和进度功能继续工作。

## 8. 错误处理

业务错误文案默认以后端返回的 `message` 为准，前端不维护重复的业务错误翻译表。

- 前端负责把后端消息放在字段、局部区域或全局提示的正确位置。
- 后端未返回可用消息时才使用通用兜底文案。
- 断网、超时、请求取消和响应解析失败使用前端本地提示。
- 保留并展示后端返回的 `requestId`。
- 401、403、404 和 429 触发对应交互，说明文案仍优先采用后端消息。
- 不展示异常堆栈、SQL、内部服务地址等敏感内容；疑似敏感响应改用安全兜底文案。
- 首版不擅自翻译后端业务消息。未来多语言需要后端返回稳定错误标识或对应语言文案。
- 网络失败时保留用户已经填写的搜索、表单或对话内容。
- 封面失败使用统一文字占位，不显示破图。

## 9. 无障碍与性能

### 9.1 无障碍

- 目标为 WCAG 2.2 AA。
- 所有功能支持键盘操作，焦点样式始终可见。
- 弹窗、抽屉和 AI 面板正确管理焦点与关闭后的焦点恢复。
- 收藏状态、评分和进度不只依赖颜色表达。
- 支持减少动态效果、高对比度和浏览器字号缩放。
- 内容图片提供有效替代文本，装饰图片不进入读屏顺序。
- SSE 新消息不频繁打断读屏，在一条回复完成后进行温和通知。

### 9.2 性能

- 公开页面优先输出可阅读 HTML，再按需水合交互区域。
- 首页和列表使用响应式图片，不下载超出显示需求的大封面。
- AI 和收藏编辑器等重交互模块延迟加载。
- 搜索建议防抖并取消过期请求。
- 普通分页不一次性加载全部番剧。
- Client 核心页面设置 Web Vitals 预算并在 CI 中检查明显回退。
- Admin 大型表格使用服务端分页，只有真实数据量需要时才引入虚拟滚动。

## 10. 测试策略

- 单元测试覆盖纯函数、查询参数转换、错误规范化、进度计算和状态转换。
- 组件测试覆盖搜索栏、收藏编辑器、AI 操作预览、主题切换和响应式导航。
- 集成测试使用可控 API mock 覆盖登录刷新、查询失效、表单错误和 SSE 事件处理。
- Playwright 端到端测试覆盖真实关键闭环。
- CI 检查 OpenAPI 可生成，并确认生成类型与前端编译兼容。
- 自动无障碍规则检查结合关键页面人工键盘走查。
- 视觉回归覆盖首页、详情、追番、AI 展开态和 Admin 核心布局的桌面与移动尺寸。

Client 核心端到端场景：

1. 未登录浏览首页、搜索并打开番剧详情。
2. 注册、验证邮箱、登录、刷新会话和退出。
3. 收藏番剧、修改状态、评分和观看进度。
4. 查看当前季度放送时间表。
5. 打开 AI、接收 SSE、切换页面后继续对话。
6. AI 生成操作预览，确认后刷新收藏状态。
7. 预览取消、过期、Agent 中断和重新连接。
8. 浅色、深色和窄屏关键流程。

## 11. 分阶段交付

### 阶段 0：基础工程

建立 monorepo、设计 token、OpenAPI 生成、CI 和独立部署骨架。

### 阶段 1：Client 公开体验

交付首页、搜索、详情、时间表、SSR、SEO、分享元数据、响应式布局和浅深主题。

### 阶段 2：Client 用户闭环

交付认证、个性化首页、收藏、评分、自定义标签、观看进度和个人资料。

### 阶段 3：Client AI

交付桌面悬浮窗、移动底部面板、SSE、会话历史、工具状态和预览确认。

### 阶段 4：Admin 基础后台

交付登录、仪表盘、番剧、用户、导入和日志。

### 阶段 5：Admin Agent

交付模型配置、提示词、管理员对话和细粒度权限。

每个阶段都必须满足：

- TypeScript、lint、单元或组件测试和生产构建通过。
- 阶段涉及的关键端到端测试通过。
- 不保留指向旧前端的路由或半兼容代码。
- 旧前端只在新阶段达到功能等价后移除，避免一次性失去可运行基线。
- Client 与 Admin 可以独立回滚。

## 12. 成功标准

- 公开首页、搜索结果、详情和时间表返回可索引的服务端 HTML 与正确页面元数据。
- 桌面和移动端都能完整完成搜索、收藏、进度和 AI 确认流程。
- Client Token 不暴露给浏览器 JavaScript；Admin Token 不持久化到浏览器存储。
- Agent 失败不影响非 AI 业务功能。
- OpenAPI 变更能在 CI 中暴露不兼容问题。
- 两个站点可独立构建、部署和回滚。
- 关键页面达到 WCAG 2.2 AA 目标，并通过约定的质量门禁。
