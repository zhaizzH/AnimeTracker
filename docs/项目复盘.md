# 项目复盘

> 本复盘覆盖 AnimeTracker「番组手账」从零到完成核心功能的完整历程。项目从 2026-07-03 开始，至 2026-08-06 结束，历时约 5 周，共 **363 次提交**，技术栈覆盖 **双 React 前端**（用户端 + 运营后台）、**Spring Boot 后端** 与 **LangGraph AI Agent**。以下按技术演进、踩坑修复、流程协作、产品现状与核心收获五章展开，每章独立成篇。

## 0. 一句话总结

个人动漫追番管理平台，5 周从零做到「番剧库管理（追番 / 标签 / 用户）+ AI 对话 Agent + 运营后台」三大能力块。

## 1. 技术选型与演进

### 1.1 选型：一次「够用就好」的技术组合

| 层 | 技术 | 复盘视角：为什么是它 |
|----|------|----------------------|
| 前端·用户端 | React 18 + TypeScript + Vite 6 + Ant Design 5 + Zustand + React Query | `frontend/client`（:5173），生产可用 |
| 前端·管理端 | 同栈 | `frontend/admin`（:5174，预览版） |
| 业务后端 | Spring Boot 3.2 + MyBatis-Plus 3.5.5 + Java 21 | Maven 多模块，`backend/business`（:8080） |
| AI Agent | FastAPI + LangGraph + 通义千问（Qwen） | `backend/agent`（Python，:8090） |
| Agent 代理层 | Spring Boot Web（轻量转发） | `backend/business/agent` 模块 |
| 数据层 | MySQL 8 + Redis + MinIO | 业务数据 / 缓存与会话 / 对象存储 |
| 数据导入 | Python 3.10+ + SQLAlchemy + Requests | `backend/agent/importer`，数据源 Bangumi |

几个选型点的复盘口径：

- **前端从 Vue 迁到 React，是早期的一次「纠偏」**。项目 07-03 用 Vue3 + Pinia + Tailwind 起步，推进到中段（07-26）整体切换到 React 生态——先落 React 脚手架（提交 `efbde68`），再删掉 Vue 前端（提交 `3e64303`）。README 技术全景专门标注「前端技术栈为 React 生态（非 Vue）」，可见这是一次有意识的定向：React + AntD 的组件生态与 TypeScript 类型推导在后续推进中明显更顺手。代价是前半程 Vue 页面（登录、注册、仪表盘等）作废重写，但这笔沉没成本在 5 周的整体交付里可以接受。
- **双前端共用一套 API**。用户端与运营后台是各自独立的 Vite 应用，但都通过 Vite 代理把 `/api` 转发到 `http://localhost:8080`。拆两个应用而不是一个应用两条路由，是因为两者的访问者、信息密度、组件形态差异大，独立演进、独立构建互不牵制；代价是多维护一套脚手架。管理端当前是预览版（登录 + 仪表盘可交互，其余页面骨架陆续接入）。
- **后端一个 Maven 多模块，Agent 只做转发层**。业务后端拆成 `common / pojo / admin / client / agent / app` 六个模块（提交 `67037fd` 完成多模块重构）。Java 侧不直接做大模型推理，`agent` 模块只是一个轻量 HTTP 转发层；真正的 LangGraph 图跑在独立的 Python FastAPI 服务里。这是「LLM 生态在 Python 最成熟、业务 API 在 Java」的现实折中（详见 1.3 决策二）。
- **数据导入独立成 Python 进程**，不占用 Java 主链路。Bangumi 源有严格的限流，导入器（SQLAlchemy + Requests）自带限流重试与清洗，手动或定时触发，带崩了也不影响主服务。
- **存储三件套分工明确**：MySQL 8 主库（业务数据）、Redis（缓存 + 会话 + 提示词，JWT 令牌白名单也在 Redis，登出即失效）、MinIO（封面与头像转存）。

### 1.2 演进时间线：Agent 目录的「最后一晚收敛」

Agent 是功能推进期自然生长出来的：Redis 会话、SSE 引擎、域节点在 7 月底一个个落地，目录渐渐叠成 `client/domain/<域>/node.py + tools.py`、`tools/`、`client/state.py` 这种嵌套。到项目最后一天 08-06 晚上 22:41–22:51，十分钟内连续六个 refactor，把 Agent 结构收敛成「入口 → 图 → 域 → 共享管道 → 共享工具 → 引擎」的规整分层。逐个复盘：

1. **`61781ff` core/agent 上提为 `core/`（消除双 agent 命名空间）**。当时 `app` 下有两处「agent」——`app/agent/*`（图与工具）和 `app/core/agent/*`（`agent_runtime`、`event_bus`、`middleware`、`streaming` 这些引擎），同一个词指两层东西，读代码得先分辨是哪个 agent。动作：引擎整体上移一层变成 `app/core/*`。收益：命名空间收敛，import 变短，语义变成「core=引擎，agent=图与领域」。

2. **`8759e5f` 共享工具 http / time_tool 收拢到 `agent/` 根**。统一 HTTP 助手 `_http.py` 埋在 `client/domain/` 深处、`time_tool.py` 单独占一个 `tools/` 目录，而它们被各域与 admin 共用。动作：上提到 `app/agent/http.py` 与 `app/agent/time_tool.py`，删除 `tools/` 目录。收益：共享工具与领域文件同层、复用即所见，「都往里塞」的 `tools/` 篮子消失。

3. **`5fe7a3e` state 上提为 graph 级 `app/agent/state.py`**。`AgentState` 原先定义在 `client/` 下，但 admin 节点、gateway 路由都在引用它——图的 state 不该从属于某个 client 域。动作：`client/state.py → app/agent/state.py`。收益：state 归属图而非域，为下一步图装配上提铺路。

4. **`8e0050a` client/domain 扁平化，一域一文件**。每个域原先是一个目录（`node.py` + `tools.py`），域之间靠目录跳转，且 `node.py` 多半只是「把 tools 列表塞进 agent」的薄壳。动作：`search / discover / recommend / router` 四个目录拍平为 `client/search.py`、`discover.py`、`recommend.py`、`gateway.py`，薄壳并入同文件，`user_collections_tools.py` 归位为 `collections.py`。收益：域 = 一个文件，加域改域不再跨目录。

5. **`9633605` 三 client 域节点抽 `run_domain_agent` 共享管道**。`search / discover / recommend` 三个节点各约 37 行，做的却是同一件事——`create_agent` + 流式跑 + 攒消息回包，只是 slot / tools / prompt 不同，三份几乎相同的管道是明显的复制。动作：抽出 `app/agent/run.py` 的 `run_domain_agent(state, *, slot, tools, prompt_key, prompt_path)`，三域文件瘦身为「定义 tools + 调共享管道」（净 -85 行）。收益：域与管道解耦，新域节点只需传参；管道逻辑只写一遍，改流式、改中间件只动一处。

6. **`e4c36af` 图装配上提为 `app/agent/graph.py`，删死代码 `langgraph_app`**。图装配 `build_graph` 原先叫 `client/workflow.py`，藏在 client/ 下；同时 `client/langgraph_app.py` 是旧装配残留的死代码，`main.py` 已不再需要。动作：`workflow.py → app/agent/graph.py`，删除 `langgraph_app.py`。收益：图装配与 `state.py`、`run.py` 同层，「入口 → 图 → 域 → 管道」四层完整；死代码清零。

六步收尾连成一气：把功能推进期自然生长的结构，收敛成一眼能读完的形态——`main.py` 只做启动接线，`graph.py` 只做图装配，`client/` 每域一个文件，`run.py` 一份共享管道，`http.py` / `time_tool.py` 共享工具，`core/` 引擎独立成层。

### 1.3 关键决策与代价

**决策一：`InjectedState` 注入用户上下文，让业务工具「拿身份」。**
Agent 只读地搜番剧、查详情容易；一旦要读「我的收藏」「我的观看画像」，工具就必须知道当前用户是谁、该用谁的 token 回查业务 API。而 `@tool` 函数只接收 LLM 给的参数——让 LLM 去传 `user_id` / `token` 既不可靠也不安全。方案是用 LangGraph 的 `InjectedState("user")` 把图 state 里的 `UserInfo`（`user_id / username / role / token`）直接注入工具参数，LLM 既看不到也不传这两个参数（见 `client/collections.py` 里 `get_my_collections` 等工具的 `user` 参数）。三个提交把链路打通：

- `79455d0` 先写测试，验证 `create_agent` 的 InjectedState 机制能注入用户上下文，`UserInfo` 增加 `token` 字段（默认空串）供断言；
- `9506254` JWT 解析后写入 `UserInfo` 与初始 state（`api/deps.py`、`service/chat.py`），token 进入 state；
- `1896fe2` `agent_stream` 透传完整 state（而非仅 messages）作为初始状态，工具才真正读到注入值。

代价与取舍：state 里带 token，意味着 Agent 进程握着用户的凭证，安全边界靠「工具只把 token 传给 business API、绝不让 LLM 见到」来守；同时 Agent 用与业务后端共享的 `JWT_SECRET` 本地验签（README .env 注明「agent 本地验签，不回调业务后端」），把鉴权从「每次转发都验」降为「进入会话时验一次」，省一次网络往返——代价是 JWT 密钥必须 Java / Python 两处同步，密钥轮换要两边一起改。

**决策二：Agent 请求链路「前端 → Java 转发层(:8080) → Python(:8090) → 回查 business API」。**
LLM 能力天然在 Python 生态，业务 API 在 Java。如果让浏览器直连 Python，会多开一个端口、多一套 CORS 与鉴权边界。于是最终形态（README「系统架构」图）：浏览器只认 `:8080`——Vite 代理 `/api` → 8080，business 的 `agent` 模块把 `/api/agent/*` 转发到 Python FastAPI（:8090），Python 的工具调用再用 `BACKEND_BASE_URL`（`http://localhost:8080`）回查业务 API。一次 Agent 对话，数据在前端 → Java → Python → Java → Python → Java → 前端之间折返。SSE 长连接由 Java 侧用无读超时 RestTemplate 转发（提交 `94e3c85`），避免思考型模型首段超时断流。

代价与取舍：多一跳 = 多一份转发代码（`AgentController` / `AgentServiceImpl`）与可调参的连接配置（`at.agent.host` / `at.agent.port`），排障要跨 Java / Python 两头查日志。换来的单一入口、统一鉴权与 CORS、Python 服务保持内部不直接暴露，对一个要持续加 Agent 能力的项目是划算的——这是一笔「用后端复杂度换边界清晰」的交易。

### 1.4 做得好 / 待改进

**做得好**
- 重构纪律严格：最后一天那一串 refactor 全程零死代码残留——`langgraph_app`、`tools/` 目录、`client/domain` 旧路径，每个收敛动作都把旧路径一并清掉，不留双份；「同一个词指两层」的命名混乱没有带进下一阶段。
- 决策先测后写：InjectedState 链路是「先写测试验证机制可行（`79455d0`），再接线（`9506254` / `1896fe2`）」，方向验证成本很低，而不是先改代码后补测。
- 共享管道及时提取：三个域节点长到约 37 行重复时立刻抽 `run_domain_agent`，没有让复制再翻一倍才动手。

**待改进**
- Agent 结构前期未一次到位。从功能推进期的 `client/domain/<域>/node.py + tools.py` 嵌套，到最后一天才经多轮上提 / 扁平化收敛，期间读代码的人要反复适应目录跳变。若重来，第一天就按「入口 → 图 → 域 → 共享管道 → 共享工具 → 引擎」分层：每域一个文件、共享工具不埋在域深处、state 从 graph 级定义、图装配直接放根层，能省掉这批迁移 diff 与伴随的 import 反复调整。
- 跨语言 schema 对齐依赖文档与人工。Java（MyBatis-Plus 实体）与 Python（importer 的 SQLAlchemy 模型）共用一张 `anime_tracker` 库，靠 `docs/db-schema.sql` 与两边的 .env 对齐，字段漂移只能靠联调暴露；若引入由建表脚本生成的模型或校验，能把这类问题前移。

## 2. 踩坑与修复

开发中的坑集中在两块：基础配置（连接池、映射路径、日志）与安全防护（验证码、限流）。每个坑按「症状→根因→修复」记录，并锚定当时的修复提交，可回溯核对。

**坑 1：Hikari 连接超时（`f1e2ce0`）**
症状：DB 不可用时，连接获取最长要挂 20s 才报错，接口表现为长时间卡顿后超时。
根因：HikariCP `connection-timeout` 配了 20s，等待时间过长。
修复：收紧到 5s，DB 不可用时快速失败——把「慢失败」换成「快失败」。

**坑 2：MyBatis-Plus mapper-locations 路径（`95fe65a`）**
症状：本地能起、部署后部分 XML 自定义 SQL 没生效，是典型的「配置没在真实启动路径验证」。
根因：`mapper-locations` 路径格式写错，XML 映射文件压根没被扫描加载；顺带 SubjectMapper 接口注释格式也不规范，一并修正。
修复：修正路径格式，确认 XML 映射被正确加载。

**坑 3：Resend 客户端每次请求 new（`afb9579`）**
症状：发送验证码邮件时每次都新建一个 Resend 客户端，连接无法复用。
根因：客户端在 service 里按请求 `new`，没有交给 Spring 管理。
修复：抽成 `ResendConfig` 单例 bean，注入复用。

**坑 4：番剧查询 N+1（`12b6db6`）**
症状：番剧列表/详情查询偏慢，存在循环内逐条查库的 N+1 放大。
根因：查询链路残留死代码，叠加循环逐条查询，放大了 DB 往返次数。
修复：清理死代码并修复 N+1，减少 DB 往返。

**坑 5：验证码防爆破（`6650bfc`）**
症状：验证码校验可无限尝试，存在暴力撞码风险。
根因：校验只有「对错」，没有失败计数与锁定。
修复：加失败计数，5 次错误锁定 5 分钟，防爆破。

**坑 6：认证接口限流（`772d8a9` / `35b897e`）**
症状：公开认证接口（邮箱验证码）可被脚本刷，邮件额度会被耗尽。
根因：接口无限流，同一邮箱 / IP 可不停触发发送。
修复：新增 `@RateLimit` 注解 + AOP 切面，按「邮箱+IP」计数限流；配套 `RateLimiter` 组件与 `RedisUtil` 的 `INCR` 能力。

**坑 7：operation_log 膨胀（`0d97eac`）**
症状：操作日志表无限增长，存储与查询压力持续累积。
根因：日志只写不清理。
修复：定时任务每天 03:30 清理 90 天前的日志，防止无限增长。

**坑 8：Agent HTTP 助手（`e56c7b3`）**
症状：Agent 的 search / discover 域各自维护一份 HTTP 调用逻辑，401 处理不一致，改动要双份同步。
根因：`_safe_call` 在多个域工具里重复实现。
修复：统一 `call_api` HTTP 助手，收编各域 `_safe_call`，并统一映射 401。

### 做得好

- 安全类修复覆盖到位：验证码防爆破（`6650bfc`）与认证接口限流（`772d8a9` / `35b897e`）成对落地，账号安全与邮件额度都有兜底，且 `RateLimiter` 组件带单元测试。
- 修复大多有测试锚定：`6650bfc`、`772d8a9`、`35b897e`、`0d97eac`、`e56c7b3` 同批提交了测试，行为被锁住，后续回归有据可查。

### 待改进

- 配置类坑是「本地起得来但部署才炸」：`95fe65a` 的 mapper-locations 路径格式、`f1e2ce0` 的连接超时，本地服务都能正常启动，问题要到真实部署环境才暴露。教训：配置变更需在真实启动路径上验证，不能只在本地起一下就认为上线安全。
- 配置改动大多没带回归验证：超时与路径这类改动只动了 `application.yml`，靠部署期人工发现，缺少「起服务后断言关键 SQL / 连接行为正常」的一步检查。

## 3. 开发流程与协作

本项目是「一个人 + AI 结对」的协作模式：从需求拆解、方案设计到实现与测试，几乎每个功能块都沿一条固定纪律推进——先写 design spec，再写 implementation plan，最后照着 plan 逐条实现并提交。这条 pipeline 走下来，全周期沉淀了 19 份 plan、17 份 design（含本次复盘自身的两份），把「改动有据可查」变成了常态。

### 3.1 流程纪律：spec → plan → implement

流程本身不难概括：接到一个功能诉求，先落一份 `docs/superpowers/specs/<日期>-<功能>-design.md`，把目标、边界、已确认决策写清楚（spec 层回答「做什么、为什么、边界在哪」）；再写 `docs/superpowers/plans/<日期>-<功能>-plan.md`，把实现拆成可执行的步骤（plan 层回答「先做什么、后做什么、每步验证什么」）；最后按 plan 逐条实现、逐条提交。以最近的 `2026-08-07-error-interception-and-conventions` 为例：design 先界定「修真实缺口 + 写规范文档 + 统一一致性」的三重动机，明确不引入 checkstyle 工具、不改错误码模型、注释保持中文，把范围钉死为全量存量手动规范化；plan 再把这些约束拆成可执行的改造清单，实现阶段照单落地。

值得坚持的：

- **复杂功能先规划，避免返工。** 用户收藏（`2026-07-19` / `2026-07-24` 两轮 plan+design）、Agent 分层（`2026-08-02`、`2026-08-06` 两轮）这类跨前端后端、牵动数据模型的功能，先把决策在 design 里定下来再动手，显著减少了「做到一半发现方案不对要回滚」的情况。第 1 章复盘过的 InjectedState 用户上下文链路（`79455d0` 先测后写）正是从 `2026-08-06-agent-user-context` 这份 plan 一路走下来的。
- **每份 plan 留下审计痕迹。** 19 份 plan 与对应 design 按日期存档在 `docs/superpowers/`，任何一次重构、任何一个功能都能回查到当时的决策与取舍；写这份复盘本身就直接受益于这些存档。

可精简的：

- **小改动也走完整 spec → plan，略显重。** 改配置、单点修复这类改动（如第 2 章的 `f1e2ce0` 连接超时、`95fe65a` 路径修正）其实直接改 + 补测即可，为它们各写一份 design + plan 的边际价值有限。建议后续按改动面分级：小改（配置、单点修复、纯样式）直接做并留清晰提交说明；大改（新增能力、跨模块重构、数据模型变更）才走完整 spec → plan 流程。分级标准甚至可以写进 plan 模板，作为「该不该写 plan」的默认判断。

### 3.2 测试策略

测试重心放在了最难看测试、最容易跑偏的 Agent 层。Agent 的核心价值是对话 turn 里的工具编排与状态流转，而这类逻辑依赖 LangGraph 运行时、工具注入与消息流，最难用单测锁死。项目的应对是「端到端 turn 测试兜底」：`backend/agent/tests/` 下共 22 个测试文件，覆盖 runtime、流式、SSE、域节点、HTTP 助手与工具层，其中两条主线：

- **Agent 完整 turn 集成测试（`182ab99`）**：把「用户收藏工具挂载到三域」这一步同批落地了一份完整 turn 的集成测试，从入站请求一路跑到工具返回，验证整条链路在真实图装配下的行为，而不只是某个节点的单点逻辑。
- **`create_agent` InjectedState 机制验证（`79455d0`）**：在第 1 章复盘过的 InjectedState 链路里，先写测试验证 `create_agent` 能把 `UserInfo` 注入工具参数、LLM 既看不到也不传这两个参数，方向验证通过后再接线（`9506254` / `1896fe2`）；收藏工具自身的单测（随 `acbae76` 同批落地）进一步锁住「全只读」的工具行为。

一句话归纳测试策略：**复杂难测的逻辑，靠最少但真实的端到端 turn 测试兜底；能单测的工具行为，单独锁死。**

相对地，前端测试是明显短板。两个前端（`frontend/client`、`frontend/admin`）均无单元 / 组件测试文件，交互正确性以手动验收为主——追番操作、收藏面板这类核心交互靠人肉点一遍确认。这个选择在 5 周的个人项目里可以接受（手动验收成本低于搭建前端测试脚手架的成本），但页面交互一旦增多，前端回归会开始依赖记忆，届时应补一层组件测试。

### 做得好

- **规划纪律与测试兜底互相咬合。** 复杂功能先 design 再 plan 再实现，难测的 Agent 逻辑用端到端 turn 测试兜底，测试反过来锚定规划（先写测试验证机制、再接线）。纪律不是悬空的流程，而是每次改动都能在 `docs/superpowers/` 找到决策、在 `backend/agent/tests/` 找到对应验证。
- **审计痕迹完整。** 全周期 19 份 plan、17 份 design 按日期归档，连本次复盘本身也是这套流程的一部分——写这一章时能直接回查每一份当时的决策。

### 待改进

- **流程缺分级。** 小改动也走完整 spec → plan，拖慢节奏。应引入「小改直接做、大改走 spec」的分级（见 3.1），把流程成本花在真正需要规划的功能上。
- **前端测试覆盖弱于后端。** 两个前端零测试文件，交互靠手动验收，回归依赖记忆，风险暴露面集中在 Agent 层（23 个测试文件）与业务后端（10 个），前端暂时裸奔。后续页面交互增多时应补组件测试。

- **三大能力块分工明确**：番剧库 / 追番 / 标签构成数据底座，Agent 是消费这些数据的交互层，数据导入器解决底座的冷启动来源——产品闭环与实现分层一一对应，新增能力能顺着这条链自然落位。

## 5. 核心收获 Top 3

这三条不是并列的技巧清单，而是从前面四章的「做得好 / 待改进」里反复出现的同一条底线上长出来的判断：**结构允许生长、决策先想后做、安全与健壮性不打折**。

**收获一：重构纪律 > 一次性完美设计。**
第 1 章那串 Agent 收敛（`61781ff` → `e4c36af`）证明了「先跑通再收敛」这条路走得通：功能推进期允许结构自然生长，等看清真实形态再一次性收敛，全程零死代码残留。它比一开始就按想象套一个「完美目录」更稳——前期你并不知道哪些文件会被共享、哪些会成长为什么形态，硬套结构只会提前写下注定要改的迁移 diff。**下次怎么做**：不禁止「先跑通」，但给结构设一个明确的收敛触发点——出现双命名空间、三处以上复制、目录嵌套超过两层，一到点就停下来重构，不让生长拖成无法收拾的形状。

**收获二：先想后写，复杂功能走 spec → plan 省返工。**
第 3 章流程纪律的正面印证是用户收藏与 Agent 分层：跨前端后端、牵动数据模型的功能，先把决策在 design 里钉死再动手，显著减少「做到一半发现方案不对」的回滚；InjectedState 链路更是「先写测试验证机制（`79455d0`）、再接线」的典型。同一章「待改进」也给出了反面代价：小改动同样走完整流程，拖慢了节奏。**下次怎么做**：按改动面分级——小改（配置、单点修复、纯样式）直接做并留清晰提交说明，大改（新增能力、跨模块重构、数据模型变更）才走完整 spec → plan；把分级标准写进 plan 模板，作为「该不该写 plan」的默认判断。

**收获三：安全与健壮性不能省，且要成对落地。**
第 2 章的安全类修复是成对落地的：验证码防爆破（`6650bfc`）与认证接口限流（`772d8a9` / `35b897e`）把账号安全与邮件额度一起兜住；健壮性修复（连接超时快失败 `f1e2ce0`、日志清理 `0d97eac`、N+1 `12b6db6`）几乎都各带测试锚定。它们共同指向一句话：限流、锁定、超时、日志清理、慢查询，是上线前就该有的兜底，而不是出了问题再补的补丁。**下次怎么做**：把这份清单沉淀成项目级的发版前检查单，每次上线前对照过一遍；配置类变更在真实启动路径上验证（第 2 章 `95fe65a` 的教训），不能「本地能起」就当「上线安全」。

三章复盘各写各的，落到行动上是同一件事：结构允许生长、决策先想后做、安全与健壮性不打折——这是这个「一个人 + AI 结对」的项目里，最想带进下一个项目的东西。
