# AnimeTracker 测试计划编写方案

> 版本：v1.0（2026-08-10）
> 依据：对 `docs/test-plan.md` v1.2 的评审结果，以及本次 L0-L4 实际执行中暴露的问题。

## 1. 评审结论

现有计划已经具备可执行性的基础：分层明确（L0-L4）、顺序清晰、安全链路重点突出、包含风险表和报告模板，也规定了不得泄露凭据、不得提交 git。主要问题不在于“要不要分层”，而在于**用例没有唯一编号、断言不够具体、数据没有准备与清理、环境假设不可移植**，导致执行结果依赖执行者临场判断，报告里的通过率也无法从计划直接推导。

需要改进的关键点：

| 现有问题 | 影响 | 编写方案 |
|---|---|---|
| 用例没有 ID 和总数 | 报告计数口径不一致，漏测不易发现 | 每个用例分配唯一 ID，计划直接给出总数 |
| 期望结果写得太粗 | 同一接口可被不同人判为通过或失败 | 写清请求、响应状态码、响应体结构、关键字段断言 |
| 没有测试数据准备和清理 | 收藏、锁定、导入等用例会污染环境 | 明确 fixture、reset 脚本、专用账号、执行前后数据校验 |
| 环境信息不可移植 | 绝对路径、机器假设导致换机即失效 | 用相对路径/环境变量，给出 readiness 检查命令 |
| 没有准入/准出标准 | 服务未就绪也继续执行，结果不可信 | 设置 smoke gate 和 exit criteria |
| L4 浏览器步骤过粗 | 只写“走查”，没有 URL、操作、断言 | 每页一个可执行的步骤表，并指定截图证据 |
| 缺陷处理没有闭环 | “修复并复测”缺少确认步骤 | 明确记录、复测、回归的三段流程 |
| 报告模板缺少“受限”状态 | 环境受限和跳过混在一起 | 状态统一为 PASS/FAIL/SKIP/LIMITED |

## 2. 编写原则

1. **用例可追踪**：每个用例对应一个需求或验收标准，测试计划中附需求覆盖矩阵。
2. **用例可重放**：任何人拿到计划都能按相同顺序、相同数据、相同命令执行。
3. **预期可判定**：每条期望至少包含 HTTP 状态码或 UI 状态，以及至少一个可断言字段。
4. **数据可恢复**：测试开始前记录基线，测试结束后恢复或清理，破坏性用例使用隔离账号。
5. **结果可统计**：用例总数、通过数、失败数、跳过数、受限数在计划中可直接汇总。
6. **计划与报告分离**：计划只定义怎么做和判定标准，报告只记录执行结果，报告引用计划中的用例 ID。

## 3. 标准结构

### 0. 元信息

- 计划版本、生效日期、适用范围
- 被测系统版本：分支、commit、前端版本、后端版本、数据库 schema 版本
- 执行人角色、预计时长

### 1. 目标与范围

- 测试目标：用可验证的验收标准描述，例如“登录接口在连续 5 次错误后必须锁定”
- 纳入范围：明确列出模块
- 不纳入范围：明确列出，避免误测
- 需求覆盖矩阵：需求/验收项 → 用例 ID

### 2. 环境与准入条件

- 服务清单：进程、端口、健康检查 URL、期望状态
- 依赖清单：MySQL、Redis、MinIO、外部模型服务，附 `docker ps` / `curl` 检查命令
- 测试数据基线：账号、fixture、当前数据量
- 准入标准：所有 readiness 检查通过，否则进入环境问题处理流程

### 3. 测试数据管理

- 正常用例使用 fixture 数据，避免依赖生产数据
- 破坏性用例使用专用隔离账号，例如 `e2e_lock_test`
- 每个用例注明：前置数据、执行后预期、清理动作
- 提供数据准备脚本和清理脚本，统一放在 `scripts/test-fixtures/`

### 4. 用例清单

每个用例使用以下字段：

| 字段 | 说明 |
|---|---|
| ID | 唯一编号，例如 `API-AUTH-003` |
| 优先级 | P0/P1/P2 |
| 前置条件 | 账号、数据、服务状态 |
| 步骤 | 可执行的编号步骤，含 URL、请求体、操作路径 |
| 期望结果 | 状态码、响应结构、关键字段、UI 状态 |
| 清理 | 恢复数据、退出登录、删除测试记录 |
| 证据 | 截图、日志、命令输出 |
| 状态 | 执行后填写 PASS/FAIL/SKIP/LIMITED |

### 5. 执行顺序与缺陷流程

- 顺序执行：环境检查 → 单元层 → 接口层 → 端到端
- 缺陷处理：记录复现步骤 → 判定严重度 → 按约定决定是否本地修复 → 修复后执行该用例及关联回归
- 明确“是否自动修复”由任务指令决定，计划不默认改写代码

### 6. 风险与退出标准

- 风险表：环境、数据、外部依赖、长连接
- 退出标准：无 P0，P1 有明确处置结论，覆盖率达标
- 阻断标准：核心依赖不可用且 30 分钟内无法恢复时停止该层

### 7. 报告模板

- 执行环境：版本、时间、服务状态、数据基线
- 结果汇总：按层列出用例数/通过/失败/跳过/受限/通过率
- 失败明细：用例 ID、期望、实际、复现步骤、严重度
- 受限明细：受限项、原因、补测条件
- 上线建议：按 P0/P1 阻断给出明确结论

## 4. 用例编号规范

建议统一格式：`{层}-{模块}-{序号}`。

示例：

| 编号 | 内容 |
|---|---|
| `UNIT-JAVA-IMPORT-001` | Java 单测：导入 URL 构造 |
| `UNIT-AGENT-CONFIG-002` | Agent 测试：模型槽位配置 |
| `API-AUTH-003` | 登录接口：密码爆破锁定 |
| `API-COLLECTION-005` | 收藏接口：重复收藏 409 |
| `E2E-CLIENT-SEARCH-002` | 用户端：关键词搜索 |
| `E2E-ADMIN-DASHBOARD-001` | 管理端：仪表盘渲染 |

编号一旦发布到计划中，后续版本不允许复用；同一用例语义变化时生成新 ID 并记录变更。

## 5. 断言规范

### 接口用例

- 必写：HTTP 状态码、`code` 字段、`data` 是否存在
- 推荐写：关键字段类型、列表长度、总数、排序规则
- 安全用例必写：错误响应中不得包含 SQL、resourcePath、堆栈、token、密码
- 长连接用例必写：Content-Type、事件顺序、首段超时、总超时、断开后的健康检查

示例：

```text
期望：HTTP 429，body.code=429，body.message 含“锁定”，body.data 为 null；
连续 5 次错误密码后第 6 次即使使用正确密码也不允许登录。
```

### 浏览器用例

- 必写：起始 URL、登录前置、点击路径、期望 URL 参数、可见文本、列表数量
- 推荐写：截图保存路径、console error 检查、无元素重叠检查
- 数据变更类用例必写：执行前数量、执行后数量、清理后数量

## 6. 执行检查单

编写阶段：

- [ ] 每个验收项都映射到至少一个用例
- [ ] 每个用例都有唯一 ID 和明确优先级
- [ ] 接口用例给出请求、响应断言
- [ ] 浏览器用例给出 URL、操作、期望结果、截图要求
- [ ] 所有破坏性用例都有隔离账号和清理步骤
- [ ] 环境检查命令可直接执行
- [ ] 用例总数可汇总，报告模板与计划口径一致

执行阶段：

- [ ] 记录被测系统版本
- [ ] 执行 readiness 检查
- [ ] 按计划顺序执行，不临场扩大范围
- [ ] 每层结束即记录结果
- [ ] 失败用例写入复现步骤和实际/期望差异
- [ ] 环境受限用例标记 LIMITED，不混入 FAIL
