# 审查与验收的判定标准

本文件回答一个问题：**一条审查结论什么情况下才算成立。**

放在 `guides/` 而非 `.agents/skills/code-review/` 是刻意的：后者被 `.gitignore` 忽略（本地接入文件），
改它只改本机。规则本体必须随仓库走，否则换机就没了。

违背这里任何一条的结论，一律按「未验证」处理，不得作为放行或驳回的依据。

## 用户可见的东西必须观测，不能读码推断

文案、标签、渲染出来的名字、排序、布局、间距——这些的判据是**屏幕上是什么**，不是源码里看起来会是什么。

读代码只能得出「可能对」；一次渲染断言或一次真实运行才能得出「是对的」。
把这类结论降级成「备注，非缺陷」的理由通常是「代码这样写也说得通」——那恰恰是失效时刻。

**实际案例**（2026-10-30）：浮层导航提示渲染成 `⚡ 已跳转到「メイドインアビス 目覚める神秘」`，
日文标题混进中文界面。openapi 里 `name` 是日文/英文名、`nameCn` 才是中文名，实现优先了 `name`。
审查读字段描述后判断「`name` 优先也说得通」，标为备注；真机一跑就看见了。

判据落地：
- 有渲染断言（`toHaveTextContent` / 快照）→ 可下结论
- 无断言但能跑起来 → 跑一次再下结论
- 两者都没有 → 写成「未验证」，**不要**写成「备注」或「通过」

## 未复现的缺陷不报

「这个将来 X 的时候会坏」而没有触发过，属于噪音：实现方要花一个回合去证伪。
写出复现命令、测试名或变异操作，否则不要列入发现清单。

## 断言要能杀掉变异

新增或修改测试时，说明「把实现改坏，哪条用例会红」。说不出来的测试是覆盖率装饰。
变异操作本身要可还原（`cp` 备份 + 事后核对 `git diff --stat`）——忘了还原看起来和全绿一样。

## 否定断言先建正向基线

`expect(x).not.toBe(...)` 只在同一用例里先把 `x` 置成期望的正向状态后才有意义，
否则测的是复位值而不是被测行为。详见 [前端质量门禁](../frontend/quality-guidelines.md)。

## 判暂存范围不看摘要渲染

用 `git diff --cached --stat` + `git diff --cached --name-only`。
`git status --short` 的输出不保证展示 `M `/`A `/`??` 两字母状态码（本机实测出现过摘要形态），
据此判断「已暂存 vs 未暂存」会读错。误暂存构建产物由 `scripts/hooks/pre-commit` 兜底。
