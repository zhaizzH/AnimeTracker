# 0001 — Agent 写操作采用「预览 → 确认 → 执行」两阶段协议

- **状态**：accepted
- **记录日期**：2026-10-12
- **相关规范**：[backend/agent-guidelines.md](../backend/agent-guidelines.md)、[guides/cross-layer-thinking-guide.md](../guides/cross-layer-thinking-guide.md#agent-写操作)

## 背景

Agent 能替用户执行写操作：修改收藏进度、加入想看、设置收藏类型、解析待确认的 Subject。这些写对象是用户的私人数据，而执行者是 LLM——一个会生成它并未被要求执行的意图的组件。

问题的要害在于失败模式的不对称：读操作幻觉的代价是答非所问，用户看得见；写操作幻觉的代价是用户账户里凭空多出或改变了一条记录，用户**看不见**，且一旦落库就不可逆。因此不能把写权限当作「读权限 + 一点点」。

此外还有第二个隐患：如果确认这件事由模型自己表述（例如模型在回答里说「已确认」），那模型既能幻觉写操作，也能幻觉确认本身。

## 决策

所有 Agent 写操作强制拆成两个阶段：

1. **预览**：模型只能产出一个待确认意图（PendingAction），暂存在 Redis，带 600 秒 TTL。**此阶段不写任何业务数据**，只回显「将要做什么」给用户。
2. **确认 → 执行**：用户在界面确认后，系统把待确认参数（含 `preview_id`）**注入**执行阶段，由 Business 做幂等写入。

关键约束是：确认参数必须来自系统注入的待确认状态，**模型不能自行构造**。模型即使编造出确认凭据也无效，因为凭据不由它提供。

## 备选方案

1. **模型直接调用写工具。** 未采纳——幻觉即写入，且对用户不可见、不可逆；这是要消灭的失败模式本身。
2. **前端二次确认弹窗，但不引入服务端待确认态。** 未采纳——确认参数仍由前端/模型侧拼装，可被伪造；也拿不到权威的用户/会话归属与幂等语义，无法保证「同一个预览只执行一次」。
3. **两阶段 + 系统注入 `preview_id`（采纳）。** 写路径上不存在模型自主执行的可能；幂等与归属由服务端保证。

## 后果

**正面**

- 写操作必须在人真正点过一次之后才发生，模型不能自主执行。
- 确认参数不可伪造，堵住「幻觉确认」这一同源漏洞。
- 预览与执行分离，使得「将要写入什么」可被展示、审计与幂等重放。

**代价**

- 每次写多一次往返和一次用户交互；对高频操作（如追番进度）体感变重。
- 引入 Redis 状态与 TTL 语义，带来新的失败面：Redis 写入失败**不得**被当作确认成功；替换旧动作失败时必须使旧版本失效或清除，否则下一次确认会执行陈旧动作。

**约束**

- 任何一层都不能绕过确认（见 guides 的「Agent 写操作」）。预存旧动作 → 替换失败 → 再次确认，是必须覆盖的最低失败路径。
