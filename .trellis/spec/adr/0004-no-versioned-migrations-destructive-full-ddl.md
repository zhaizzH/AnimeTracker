# 0004 — 不做版本化迁移：一份破坏式全量 DDL 作为唯一结构事实来源

- **状态**：accepted
- **记录日期**：2026-10-12
- **相关规范**：[database-guidelines.md](../backend/database-guidelines.md)、`docs/README.md`

## 背景

项目需要一个库结构的**事实来源**，以及一条存量库改结构的路径。多数有存量数据的中长期项目会选择：数据库迁移工具（Flyway / Liquibase）加一份只增不减的历史迁移链。

本项目的实际数据构成是决定性的：绝大部分表（Subject、Person、Episode、角色、关系、检索投影、任务队列）都是**可从上游 Bangumi 全量重灌的派生数据**；真正的用户数据只集中在少数几张表（用户、收藏、操作日志）。

## 决策

不引入任何迁移工具，也不维护前向迁移脚本。改为：

1. `docs/database/db-schema.sql` 是**唯一**结构事实来源，每条 `CREATE TABLE` 前带 `DROP TABLE IF EXISTS`，因此**只能对空库执行**。
2. 存量库改结构只有两条路：**人工 `ALTER`**（需评审），或走**重建流程**——备份用户表 → 全量执行 DDL → 恢复用户表 → `full import` 重灌派生数据。
3. `spring.sql.init.mode: never`；历史迁移脚本 `migration-002` / `migration-003` 已移除，不再回归。

## 备选方案

1. **Flyway / Liquibase + 版本化迁移链。** 未采纳——它解决的是「派生数据不可重建、结构变更必须无损可复现」的场景。本项目的数据主体可重建，为它维护一套迁移工具链和一堆一次性 ALTER 脚本，收益不抵成本。
2. **全量 DDL + 手工 ALTER / 重建（采纳）。** 把结构真值压成一份可整体执行的 DDL，并显式约定存量库的两条路径。

## 后果

**正面**

- 结构真值是**一份**文件，任何环境都能从空库一次成型，不存在迁移链漂移。
- 派生数据可随时全量重灌，无须为「保住派生数据」而写兼容迁移。

**代价与已知风险**

- 存量库结构变更**不可复现**、易漏项；无迁移记录归档位置。
- 重建流程尚未脚本化，靠手工步骤，容易漏项。
- `db-schema.sql` 含 `DROP TABLE IF EXISTS user / user_collection / operation_log`——**整份执行会清空用户数据**。

**约束**

- 严禁把 `db-schema.sql` 当升级脚本对非空库执行；执行前必须确认目标库为空，或已单独备份用户表。
- 走重建流程前必须先确认备份**可还原**。
- 上述「待补充」项已登记在 `docs/README.md`，属于明确接受的取舍，不要在不走评审的情况下引入迁移工具或一次性 ALTER 脚本。
