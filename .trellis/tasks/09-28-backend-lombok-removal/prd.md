# Replace backend Lombok with handwritten Java

## Goal

Remove Lombok from the Java Business backend so its source explicitly declares the behavior currently generated by Lombok, while preserving runtime, serialization, validation, persistence, and API behavior.

## Background

- The Java backend is `backend/business`, a nine-module Maven reactor targeting Java 21 and Spring Boot 3.2; Python `backend/agent` is outside the migration.
- Repository inspection found 150 production Java files importing Lombok and 197 Lombok imports / 214 annotation usages (including five `@Builder.Default` annotations), spanning all nine Java modules. No backend test source imports Lombok.
- Annotation families in use include `@Data`, `@Builder` (including field-level `@Builder.Default`), constructor annotations, `@Getter`/`@Setter`, `@EqualsAndHashCode`, and `@Slf4j`; Maven POMs and `backend/business/README.md` also reference the dependency.
- Affected files are predominantly `pojo` DTO/VO/Entity/model classes and constructor-injected controllers/services/adapters. The migration must preserve observable semantics rather than mechanically expanding annotations.

## Requirements

- R1: Remove every Lombok annotation from production Java sources under `backend/business`, including `@Data`, `@Builder`, constructor/accessor annotations, and logging annotations; replace their generated behavior with handwritten Java or standard-library/framework constructs. For every entity and other mutable `@Data` class, explicitly define the applicable getters and setters that Lombok generated, alongside other generated behavior. Remove all Lombok imports.
- R2: Remove every Lombok dependency/reference from the parent POM and all nine child POMs, including the managed artifact/version and direct module dependencies; remove the Lombok dependency entry from the Business README. Do not introduce another code-generation library as a replacement.
- R3: Preserve existing public method/property accessors, constructor availability and visibility, builder entry points/chaining/build behavior, field initializers and builder defaults, inheritance semantics, and logging calls. Preserve Jackson inclusion/serialization, Bean Validation annotations, MyBatis entity access/mapping, and Spring configuration/property binding.
- R4: Preserve `@Data`-generated equality, hash-code, and string behavior where callers rely on it; avoid accidental changes to sensitive-data exposure or subclass equality. Any deliberate exception requires evidence-backed justification and explicit coverage; do not silently change behavior as part of this task.
- R5: Keep changes confined to Java Business implementation/build/docs/tests needed for this migration; do not alter API fields/routes, database schema/data, Python Agent code, frontend behavior, or business rules.
- R6: Add or adapt focused regression coverage for handwritten DTO/VO accessors and constructors, builders/default values, inheritance/equality semantics where applicable, and framework binding/serialization/persistence paths affected by the rewrite.

## Acceptance Criteria

- [ ] All production Java sources in `backend/business` compile without Lombok imports/annotations; test sources also contain no Lombok usage.
- [ ] All Maven POMs and tracked backend documentation/configuration are free of Lombok dependencies/references, except this task's historical requirement record if retained as audit history.
- [ ] A repository search confirms no Lombok reference under `backend/business` source/build/docs after migration.
- [ ] Every entity and mutable `@Data` class explicitly declares the getters/setters previously generated by Lombok, preserving names, types, visibility, and primitive/boxed boolean naming; constructors, builder APIs/defaults, and relevant equality/hash/string behavior are also preserved by source review and regression tests.
- [ ] `mvn -B clean test -f backend/business/pom.xml` passes.
- [ ] `python backend/business/tools/check_javadoc.py` and `python backend/business/tools/test_check_javadoc.py` pass for the newly handwritten declarations.
- [ ] No HTTP/OpenAPI or database contract changes are introduced; working-tree changes unrelated to the task remain untouched.

### Planning correction (Phase 2 → Phase 1)

Two gaps found while executing `implement.md` step 1. Both are user-approved:

1. **Javadoc scope was under-planned.** `CheckJavadoc.java:50` checks *every* `visitMethod`, so expanding Lombok turns each generated member into a handwritten member that must carry Chinese declaration Javadoc. Measured on the full expansion: **3503 declarations, 2042 violations across 150 files** — 733 missing Javadoc (`equals`/`hashCode`/`toString`/`canEqual`, constructors) and 1309 missing/incorrect `@param`/`@return`/`@return count=0` (builder methods and copied-but-untagged accessors). The existing spec exemption for "Lombok/编译器生成的构造器、访问器" (`quality-guidelines.md:210`) lapses once those members are handwritten. Decision: **keep the spec as-is; write Javadoc for every migrated member.** Accessor Javadoc must derive from real field semantics, not mechanical "获取 X 字段" templates, which the spec explicitly rejects.
2. **Expansion method.** Decision: **use Lombok's own `delombok`** (one-off migration tool, already present at `lombok-1.18.30.jar`; introduces no build-time code-generation dependency, satisfying R2). Delombok emits semantically exact `equals`/`hashCode`/`toString`, `$default$` builder-default handling, `is`/`get` boolean naming, and constructor ordering — removing the design's top-ranked risk of signature drift. Its output then needs cleanup: strip the timestamp header, drop `@SuppressWarnings("all")`, and de-qualify generated names.

## Out of Scope

- Removing Lombok from non-Java backends, third-party/generated code, or unrelated repositories.
- Refactoring DTO/entity mutability or replacing classes with records/immutable types unless strictly required to reproduce existing behavior (default approach: do not).
- Changing business logic, API contracts, persistence schema, dependencies unrelated to Lombok, or existing Javadoc policy.

## Technical Notes

- `@Builder.Default` occurs in progress result/preview types, so builder-created values and no-arg construction must be checked separately.
- `SubjectDetailVO` uses `@EqualsAndHashCode(callSuper = true)`; inherited equality/hash semantics need an explicit equivalent.
- `@Data` also generates `toString`, equals, and hashCode; generated output may include sensitive fields such as `User.password`, so characterization is required and unrelated security-policy changes are out of scope.
- `ProgressPreviewSnapshot` is serialized to Redis with Jackson, and configuration-property classes rely on JavaBeans setters; no-arg/bean accessors and binding behavior must remain compatible.
- POJO fields are subject to project-wide Javadoc requirements; handwritten generated members must meet `.trellis/spec/backend/quality-guidelines.md`.
- Baseline test commands are specified in `.trellis/spec/backend/quality-guidelines.md`; baseline counts in that spec are historical and must not be reused as this task's result.
